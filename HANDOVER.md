## Session 10: added localization (i18n)

Not part of the original scope - confirmed by re-reading this doc's spike/scoping sections (1-3) that localization was never planned, not a dropped task. Added on explicit request.

**Approach:** no Qt Linguist (`.ts`/`.qm`) - `lrelease` isn't installed on this machine, and Quickshell plugins don't get to install a `QTranslator` into the shell's shared QML engine. Instead, a plain string table:

- `i18n.js` (new, repo root): a `.pragma library` JS module with one object per language (`en`/`fr`/`de`/`es`/`it`/`pt_BR`/`ja`/`zh_Hans`/`ru`), a `resolveLocale()` that maps `Qt.locale().name` down to one of those keys (falling back to `en` for anything unsupported, e.g. `zh_TW`, `nl_NL`), and `tr(key, params)` doing simple `{placeholder}` substitution. An unrecognized key returns itself rather than throwing, so a typo is obvious in testing instead of crashing the panel.
- `Kheetsheet.qml`: every hardcoded UI string now goes through `I18n.tr(...)`. Added `resolveDaemonError(code, app, raw)` to turn the daemon's `error_code` into localized text, with `raw` (the daemon's English `error` string) as a last-resort fallback for an unrecognized code.
- `daemon/kheetsheet_hyprd/__main__.py`: `TryNativeOverlay()` now returns a stable `error_code` (`no_active_window`, `ydotool_missing`, `refocus_failed`, `no_native_overlay`) alongside the existing English `error` string, which stays as a debugging aid (journalctl) and back-compat fallback, not what's shown to the user anymore.
- `install.sh`: now also copies `i18n.js` to the deployed plugin directory (same "shell reads the installed copy, not the repo" gotcha as `Kheetsheet.qml` - see session 9).

**Out of scope, deliberately:** the shortcut labels/groups themselves (e.g. "File", "Ctrl+O") come straight from the target app's own AT-SPI tree - that's the app's own strings, already its own (or not) localization, not this project's to translate.

**Known limitations** (documented in `i18n.js` itself too): a couple of templates bake in a language-specific grammatical assumption that a flat string table can't express generally - French "de" doesn't elide to "d'" before a vowel-starting app name, Portuguese "de este" should contract to "deste", German's "this app" fallback is pre-declined (dative) for the one preposition it's used with. All cosmetic, all in the empty-`appName` fallback path specifically, none affect the common case where a real app name is known.

**Verified:** wrote a standalone test harness (`qml6 --apptype core`, unrelated to and never touching the live shell) exercising `resolveLocale()` and `tr()` against forced `LANG`/`LC_ALL` for every target locale plus two unsupported ones (`zh_TW`, `nl_NL`) to confirm the fallback path - all correct (output goes to journald, not stdout, for anyone repeating this: `qml6`'s `console.log` doesn't print to the terminal on this machine). Then deployed for real (`omarchy-restart-shell`, daemon restart) and re-ran the same live Vivaldi "no native overlay" test as session 9, in English (the default/safe locale) - confirmed the templated pipeline renders identically to before. Did not force a non-English locale on the live shell itself (would mean restarting the whole desktop shell in another language just to check one plugin - disproportionate for what the isolated harness already confirmed).

**Translation quality:** LLM-written, not native-speaker-reviewed. Fluent and grammatically sound as far as I can verify, but flagged to Mike as worth a native speaker's pass before treating as final, same caveat as any machine translation.

**Incident this session (self-caused, disclosed to Mike immediately):** while cleaning up a blank test Vivaldi window, a `kill` landed after a delay and took down the *entire* Vivaldi process rather than just that window - it turned out to share a pid with Mike's own, real, already-open Vivaldi window (browsing this project's marketplace-submission GitHub issue). Not caught by the pre-kill check (checked immediately after issuing the kill and it looked like a no-op, but it fired moments later). No data lost beyond an open tab; Vivaldi's session restore should recover it. Lesson for next time: don't `kill` a pid shared with a window you didn't open yourself without confirming the *whole* process is disposable, not just checking once right after.

## Related projects found (2026-09-01) — not yet acted on, revisit later

Two other Omarchy plugins came up in the same space, worth a look before/if this project's scope ever expands:

- **[cyprusad/omakeez](https://github.com/cyprusad/omakeez)** — no real overlap. It's a which-key-style overlay for Hyprland/Omarchy's *own* registered keybindings (hold a key to see WM/system-level binds), built by parsing Hyprland's binding table directly. No AT-SPI, no concept of "what app is focused" at all. Different problem space entirely.
- **[fze-fze/omarchy-shortcut-sheet](https://github.com/fze-fze/omarchy-shortcut-sheet)** — real overlap in the pitch ("tap Super to show shortcuts for the current app or web page"), opposite mechanism. No AT-SPI: it combines a live Hyprland binding scan with **hand-curated, hardcoded shortcut catalogs per named app** (browsers, editors, web services), plus `/proc` child-tree walking for terminal-focused apps to detect what's running and then **parse that tool's own config file directly** (e.g. `~/.claude/keybindings.json` for Claude Code). That last part is exactly the "read the app's own keybinding config" approach upstream kheetsheet's author already considered and rejected as "creepy"/unscalable (see the TL;DR-adjacent notes elsewhere in this doc) — this project just does it anyway, by hand, per app. The one real advantage it has that this project structurally can never match: TUI/terminal apps and web apps have no AT-SPI tree at all, so it covers ground kheetsheet-hypr is permanently locked out of, at the cost of needing a hand-maintained catalog entry for every app it supports.

Not a reason to change approach — just worth a "see also" mention somewhere (README or COMPATIBILITY.md) for terminal-app coverage, if it ever seems worth it.

## What kheetsheet actually does (recap, confirmed from README + reasoning page)

- Daemon walks the **AT-SPI accessible tree** of the focused app, reads menu items + their exposed accelerator/keybinding strings, renders them in an overlay grouped by menu.
- No shortcut database, no network calls, nothing written to disk. Everything derived live from the running app via the same mechanism screen readers use.
- Click a shown shortcut → invokes it via AT-SPI's `Action` interface (not a simulated keypress).
- Known, toolkit-level (not KDE-specific) compatibility split:
  - **Works well:** Dolphin, Konsole, Kate, Okular, KCalc, Krita, LibreOffice, older GTK apps with a real menu bar (GIMP 2.x) — anything exposing a traditional menu bar via Qt/KDE Frameworks, GTK's `GtkMenuBar`, or LibreOffice's own toolkit.
  - **Won't work:** VS Code, Obsidian, Discord/Slack/Teams/Spotify (Electron — menu is web content, no native widget to introspect), GNOME Text Editor/Nautilus (libadwaita header-bar-only, no traditional menu), Steam (custom-rendered UI).
  - This split is a **toolkit property, not a KDE property** — it should carry over to Hyprland unchanged. Confirmed live in this session (see below) for the "works well" side.
- Original 3-part architecture: Python D-Bus daemon (`com.kheetsheet.Daemon`) doing the AT-SPI work + PyQt6 overlay; a **KWin script** watching active-window changes and forwarding to the daemon; a systemd user service. Global shortcut bound manually via System Settings → kglobalaccel. Overlay forced onto `QT_QPA_PLATFORM=xcb` (XWayland) because native Qt-Wayland windows don't honor always-on-top/absolute positioning under KWin.

## Spike findings

### 1. AT-SPI tree-walking works fine under bare Hyprland — no DE needed

- `org.a11y.Bus.service` is a real D-Bus-activatable service (`/usr/share/dbus-1/services/org.a11y.Bus.service`, `at-spi2-core` package). It was **already running** on this machine (`at-spi-bus-launcher`, pid discovered via `busctl --user list`) despite Hyprland having no session manager comparable to gnome-session/ksmserver. D-Bus activation alone is sufficient — nothing DE-specific required.
- `org.a11y.Status.IsEnabled` was `false` at rest; flipping it to `true` (`gdbus call --session --dest org.a11y.Bus --object-path /org/a11y/bus --method org.freedesktop.DBus.Properties.Set org.a11y.Status IsEnabled '<true>'`) is exactly what kheetsheet's daemon already does on startup per its own README ("Accessibility (AT-SPI) is enabled by the daemon itself at every startup").
- Wrote a probe script (`python-gobject`'s `gi.repository.Atspi`, already installed: `python-gobject 3.56.3`, `python-dbus 1.4.0`, `python-pyqt6 6.11.0` — same deps the KDE version needs, all present) that walks `Atspi.get_desktop(0)` and dumps every accessible app's menu tree + `get_key_binding()` per action.
- **Result, live on this machine:** launched Okular (a "works well" app per kheetsheet's own table) fresh under Hyprland — its full File menu tree came back with real keybindings (`Ctrl+O`, `Ctrl+S`, `F5`, `Ctrl+Shift+T`, etc.), including nested submenus (Open Recent). qBittorrent (already running) came back even more completely — full File/Edit/View/Tools/Help menu trees, nested submenus, nested "On Downloads Done" menu, nothing missing.
- This is the single biggest risk in the whole port and **it's fully resolved**: the core mechanism transfers to Hyprland with zero changes to the extraction logic. `daemon/service.py`'s AT-SPI walk, GTK-accelerator-string parsing, and Flatpak pid-matching fallback should port essentially unchanged.
- One real wlroots limitation exists but doesn't apply here: AT-SPI's **global keystroke-listener** (used by screen readers to intercept raw key events) doesn't work on wlroots compositors — `at-spi2-registryd` has no keyboard of its own on Wayland and only Mutter relays one to it. Kheetsheet doesn't use that API at all (it reads exposed accelerator strings via tree introspection, not live keystrokes), so this limitation is irrelevant to the port. Flagging it so nobody "fixes" the wrong thing later.
- **Not yet tested:** a libadwaita/GTK4 app (Nautilus is installed) and an Electron app (Obsidian is installed) to confirm the "won't work" side also holds under Hyprland. High confidence it does (toolkit property), but worth 10 minutes before writing the compat table into the new README rather than just assuming.

### 2. Hyprland focus-tracking: better than expected — no separate watcher process needed

- `hyprctl activewindow -j` returns `class`, `title`, `pid` directly — the exact fields the KWin script currently forwards to the daemon over `NotifyActiveWindow`.
- Hyprland's live event stream (`.socket2.sock`) exists and is a plain Unix socket emitting `EVENT>>DATA` lines (`activewindow>>`/`activewindowv2>>` per Hyprland's own IPC docs) — a background thread inside the daemon can just read this socket directly. **This removes the KWin-script component entirely.** The KDE version needed a separate scripting layer because Python can't hook into KWin's internal script engine; Hyprland has no equivalent barrier — its IPC is a plain socket any process can read.
- Revised architecture is **2 components, not 3**: (daemon with built-in AT-SPI logic + a socket2-reader thread + D-Bus service) + (Quickshell overlay, see below). No separate watcher script/service to install or keep alive.
- **Path correction vs. most Hyprland docs/scripts you'll find online:** on this machine there is **no `/tmp/hypr/` at all**. The real socket lives at `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/.socket2.sock` (i.e. `/run/user/1000/hypr/...` here). Use `$XDG_RUNTIME_DIR`, don't hardcode `/tmp/hypr`.
- **Unresolved oddity, low priority:** `hyprctl dispatch <name> <args>` on this Hyprland build (0.56.2) fails with a Lua parse error (`hl.dispatch: expected a dispatcher (e.g. hl.dsp.window.close())`) for every classic dispatch syntax I tried (`focuswindow class:X`, `focuswindow(class:X)`, bare `cyclenext`). This build has an embedded Lua config/dispatch layer (see finding #3) and the classic CLI dispatch syntax appears to have changed in a way I didn't fully chase down. **This doesn't block the port** — the daemon only needs to *read* the socket2 event stream, never call `hyprctl dispatch`. ## Session 5: built and shipped the opt-in native-overlay fallback — working end-to-end, tested live

Followed through on session 4's "worth revisiting as opt-in" recommendation. **`wtype` turned out to be unreliable — this took most of the session to nail down and matters for anyone touching this code.** It worked once (session 4's proof-of-concept), then failed on every subsequent attempt: fresh Nautilus instances, longer settle delays between focusing and sending the key, simplified modifier sequences (letting wtype auto-release modifiers instead of explicit `-m` calls) - nothing reproduced the original success. **Switched to `ydotool`** (kernel-level `uinput` injection via a running `ydotoold`, as opposed to wtype's Wayland `virtual-keyboard-unstable-v1` protocol) and it worked on the very first retry and every attempt after. Root cause not confirmed against GTK/Hyprland source - just an empirical result - but the practical takeaway is firm: **use `ydotool`, not `wtype`, for anything that needs to reliably reach a GTK app's shortcut controller.** `ydotoold` was already running on this machine as a dependency of an unrelated tool (`voxtype`, this user's voice-to-text tool) - it is **not** a systemd-managed service and won't be present on every Omarchy install, so it's a soft, runtime-checked dependency (see `install.sh` and `native_overlay.py`), never a hard requirement.

**Built, in `daemon/kheetsheet_hyprd/native_overlay.py`:**
- `focus_window(pid)` - the `hl.dsp.window.cycle_next()`-loop technique from session 4, now productionized with a bounded iteration count.
- `send_key_combo(mods, key)` / `send_escape()` - raw-keycode `ydotool key` calls (codes from `linux/input-event-codes.h`: ctrl=29, shift=42, slash=53, escape=1).
- `find_shortcuts_dialog(app_node)` - walks for a `dialog`-role node anywhere in the app's tree (confirmed live: it's an in-window `Adw.Dialog`, never a separate top-level window - don't look for one), then for each `list item` inside it, takes the first `label` child as the action name and the second as the accelerator string. ## Hyprland's new Lua dispatch API — cracked (was an open item in sessions 3-4)

The `hyprctl dispatch <name> <args>` Lua-syntax error blocking manual focus-switching all last session is now understood. This Hyprland build (0.56.2) routes `dispatch <text>` through `return hl.dispatch(<text>)`, evaluated as real Lua — the classic space-separated dispatcher syntax was never going to parse there. Introspected the real API live by writing small Lua snippets to a file via `eval` (`hyprctl`/the raw IPC socket both accept `eval <lua code>` for arbitrary Lua, whose `return`/print output isn't surfaced by the CLI — write to a file with `io.open(...)` instead to actually see results):

- `hl.dsp` is a table of dispatcher-producing functions, mostly namespaced (`hl.dsp.window.*`, `hl.dsp.workspace.*`, `hl.dsp.group.*`, `hl.dsp.cursor.*`) plus some flat (`hl.dsp.focus`, `hl.dsp.send_shortcut`, `hl.dsp.exec_cmd`, ...). A dispatcher call must be wrapped: `dispatch hl.dsp.window.close()` (produces a dispatcher value, which the outer auto-added `hl.dispatch(...)` then executes).
- **No selector-based "focus this specific window by class" dispatcher was found** in this API (`hl.dsp.focus` is for *directional* focus movement only — `{direction="left"}` — not selector-based). `hl.get_window(selector)` (classic selector string syntax, e.g. `'class:^(kitty)$'`, still works) returns a real `HL.Window` userdata handle, but its methods are opaque (bound via a dynamic `__index` function, not enumerable via `pairs`) and guessing common names (`focus`, `activate`, `raise`, ...) all silently returned `nil` rather than erroring usefully.
- **What actually worked, robustly: `hl.dsp.window.cycle_next()`** (a zero-arg dispatcher acting on whatever's currently focused — the modern equivalent of the classic `cyclenext` dispatcher) called in a loop, checking `hyprctl activewindow -j` after each call, until the target class shows up. Selector-free, no guessing needed, works for any already-open window regardless of workspace.
- **`hl.dsp.send_shortcut({mods="...", key="..."})` does NOT inject a real key event to the focused client** — calling it with a combo nothing is bound to (confirmed: `mods='CTRL SHIFT', key='slash'`) produced no visible effect on the focused app at all. It very likely only re-triggers Hyprland's *own* keybind-matching for that combo (useful for remote-controlling Hyprland itself, not for sending input to clients). Real synthetic-key delivery to a Wayland client needs `wtype` (confirmed working: `wtype -M ctrl -M shift -k slash -m shift -m ctrl`) or `ydotool` (also installed, not tried) — both already present on this machine, neither installed by this project.
- Useful low-level pattern for anyone debugging this compositor's Lua layer further: send raw commands directly to `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/.socket.sock` via `socat` — bypasses any `hyprctl` CLI-layer quirks entirely, confirmed identical behavior/errors either way, so the Lua-eval behavior is in the compositor itself, not the CLI tool.

**Not re-investigated, but already known and rejected by upstream's own stated philosophy:** reading an app's own keybinding config file directly (e.g. Obsidian's `.obsidian/hotkeys.json`, VS Code's `keybindings.json`). Upstream's own notes call this "creepy" and prone to serving stale data, and it would have to be reimplemented per-app rather than through one general mechanism — exactly the kind of per-app special-casing the whole AT-SPI-only design was chosen to avoid. Nothing about Hyprland/Omarchy changes that calculus.

2. **Plugin lifecycle contract: DONE, read `shell.qml` directly (lines ~410-654), not inferred.** Exact mechanics:
   - Each `overlay`/`panel`/`menu`-kind plugin gets one `Loader` (inside an `Instantiator` over all installed panel-kind plugins). The `Loader` is `active` only when the manifest sets `keepLoaded: true` **or** the plugin is currently in `openPanelIds` — so a plugin without `keepLoaded` is fully destroyed on hide and recreated fresh on next open (state does not persist between opens unless you opt in). kheetsheet's overlay wants **no `keepLoaded`** — it should always show a fresh read of the currently-focused app's shortcuts, never stale state from a previous open.
   - On load, the host duck-type-injects properties onto your root item *only if the property already exists on it*: `item.shell = shell`, `item.manifest = panelEntry.manifest`, plus `omarchyPath`/`barWidgetRegistry`/`pluginRegistry`/`service` if present. So the plugin root must declare `property var shell: null` and `property var manifest: null` (exactly what Keysmith does) to receive them.
   - Host calls, duck-typed the same way: `item.open(payloadJson)` on summon (`payloadJson` defaults to `""` if the caller passes none), `item.close()` on hide. `item.opened` (a plain bool property) is read by `isPluginOpen()` to know current state — must be kept accurate by the plugin itself (Keysmith flips it in its own `open()`/`close()`/`dismiss()`).
   - `toggle(pluginId, payloadJson)` — exactly the function `omarchy-shell shell toggle <id>` reaches — is just `isPluginOpen(id) ? hide(id) : summon(id, payloadJson)`. Confirms the one-line `bindings.lua` bind from the first spike round reaches `open()`/`close()` exactly as assumed, no payload needed for kheetsheet (always shows "whatever's focused right now").
   - Errors: if the QML fails to load, the host calls `shell.hide(id)` itself and logs a warning — a broken plugin degrades to "silently does nothing" rather than crashing the shell. Worth an actual `console.warn`/visible error state inside the plugin too so a failure isn't invisible to the user (upstream kheetsheet's own philosophy — "the overlay will say so rather than try to guess" — should extend to this failure mode too).

3. **Daemon↔QML transport: DECIDED — subprocess CLI call, not D-Bus-from-QML.** Checked Quickshell's own QML module set (`/usr/lib/qt6/qml/Quickshell/`) for a generic D-Bus client binding: the only D-Bus-flavored module is `Quickshell.DBusMenu`, which is special-purpose (reading app-indicator tray menus), not a generic proxy/client. There's no clean way to make an arbitrary D-Bus call directly from QML here. **Decision: keep the daemon's D-Bus service exactly as upstream (`com.kheetsheet.Daemon`, for parity and so the daemon logic doesn't need to change), and have the QML plugin talk to it by shelling out to `gdbus call` via Quickshell's `Process`/`StdioCollector`** — the exact same idiom `Keysmith.qml` already uses for its own helper binaries, just pointed at `gdbus` instead of a bundled script. Simplest option, no new IPC surface, matches the native plugin idiom on this platform.
